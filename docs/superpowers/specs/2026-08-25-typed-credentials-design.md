# ADR-075 Typed Credentials in the Terraform Provider

Date: 2026-08-25
Status: approved, not yet implemented
Branch: `feat/adr-075-typed-credentials`

## Summary

Two additions, both backward compatible:

1. `mondoo_credential`, a resource over the credentialsV2 GraphQL API.
2. An optional `credential_mrn` attribute on `mondoo_integration_slack`,
   `mondoo_integration_github` and `mondoo_integration_aws`, mutually exclusive
   with each resource's inline secret.

No existing provider version breaks. The one schema change to existing
resources is a relaxation, described under "Backward compatibility".

The GraphQL shapes in this document were read from the server implementation at
`go.mondoo.com/server/nexus/` rather than assumed, and the reflection strategy
was prototyped against the bumped SDK before the design was fixed.

## Prerequisite: the SDK bump

`go.mondoo.com/mondoo-go` moves from `v0.0.0-20260710102002-43d8df21b0e3` to
`v0.0.0-20260822000727-1d813d6a83c7`.

Validated against HEAD before this spec was written:

| Check | Result |
| --- | --- |
| API surface diff | 127 new types, 1 removed (`OrganizationOverviewInput`, unreferenced here), 0 removed consts or funcs, 0 removed or renamed struct fields |
| `go build ./...` | clean |
| `go run ./gen` | output byte-identical to the committed files |
| `go test ./...` | fails identically before and after |

The last row is a property of the repo, not the bump: `provider_test.go` creates
a real space in `TestMain`, so the whole package needs a live organization

The pin is three months newer than the one named in the original request but
still predates all credentials work: `grep CredentialV2` returns 0 hits at the
current pin, 258 at the target.

## Decisions

### One resource, one typed attribute per kind

`CredentialV2SecretInput` is exactly-one-of 44 optional fields, server-enforced,
and the field that is set determines the kind. Three shapes were compared.

**Rejected: a shared `kind` plus a `secret` map.** Simplest to build, and the
only shape supporting `for_each` across mixed kinds. Rejected on two counts.
A key typo lands at apply rather than at `terraform validate`, so CI cannot
catch it. More importantly the whole map is one `Sensitive` attribute, so a plan
renders `~ secret = (sensitive value)` and the trap-2 failure below becomes
invisible at exactly the moment it needs to be visible.

**Rejected: one resource per kind.** 44 resource types for one concept, roughly
11,000 generated lines, 44 registry entries. It is also the only shape that
cannot be reached incrementally from either other shape.

**Chosen: one resource with 44 optional `SingleNestedAttribute`s**, one per arm
of `CredentialV2SecretInput`, under an `ExactlyOneOf`. Per-field sensitivity
means a plan shows `region` and `base_url` changing in the clear while the token
stays redacted. A typo is caught by Terraform core at validate time.

The 44 attributes are **generated**, not hand-written — see below — so the
exhaustive-map objection from the original request does not apply: nothing about
the 44 kinds is typed by hand, and a new kind arrives with an SDK bump and a
`make generate`.

### Generated by extending gen/gen.go

The original request asked whether `mondoo_credential` extends the generator.
**It does**, as a new emitter alongside `generateIntegrationResources()`, not as
a reuse of it.

44 arms of 1 to 5 flat string fields is exactly what a generator is for, and
`gen/gen.go` already reflects over an SDK input struct
(`ClientIntegrationConfigurationInput`) via mapstructure and emits schema from
`tfgen` tags. The credential arms are strictly simpler: every one of the 44 is a
flat struct whose every field is `String` or `*String`, verified across all 44.

Shared with the existing generator: `structToMap`, `toSnakeCase`,
`parseTFGenTag`, `renderTemplate`. New: one template
(`gen/templates/credential_resource.go.tmpl`), one `generateCredentialResource()`
entry point, and a sensitivity rule of its own — see below.

### Sensitivity is an allowlist, not a heuristic

`isSensitiveField` is **not** reused. Run across all 44 arms it under-marks two
genuine secrets:

| Field | Kind | What it is | Heuristic verdict |
| --- | --- | --- | --- |
| `macaroon` | `SPRITES_FLY_MACAROON` | "The Fly.io token" — a bearer token | not sensitive |
| `sas_url` | `AZURE_BLOB_SAS` | container SAS URL carrying `&sig=…` | not sensitive |

Neither contains any of the heuristic's substrings. Reusing it verbatim would
render two live secrets in plan output.

The polarity is therefore inverted: **every field is `Sensitive` unless its name
is on an explicit visible list.** Under-marking a secret is a security bug;
over-marking costs only plan legibility, so the failure mode has to point the
safe way. A new kind's new field defaults to redacted, and fields are opted into
visibility deliberately.

The visible list, every entry an identifier, endpoint or region — none a secret:

```
api_url, app_id, base_url, client_id, cloud_id, domain, email, endpoint,
fingerprint, host, org, region, server_url, subdomain, tenancy_ocid,
tenant_id, user, user_ocid, username
```

It is derived from the current 44 arms and covers every non-secret field they
have. `base_url` and `region` are on it deliberately: they are the two fields
trap 2 needs visible in a plan.

A field missing from the list is redacted, not leaked — so forgetting to extend
it when a kind is added degrades legibility rather than safety. A generator test
asserts the list contains no field the old heuristic considered sensitive, which
catches an accidental addition of a secret name.

Not reused: the integration resource template, which is welded to
`CreateIntegration`/`UpdateIntegration`/`TriggerAction` and emits one resource
per integration. Credentials need one resource containing 44 attributes over a
different mutation set.

`NewCredentialResource` is registered by hand in `provider.go`, not in
`provider_generated.go` — that file is the integration list and is regenerated
from the integration loop.

### Space or organization scope

A credential is owned by a space **or** an organization. `space_id` and
`scope_mrn` are both optional and conflict with each other, following
`export_s3_bucket.go`, `export_gcs_bucket.go`, `export_bigquery.go` and
`integration_audit_log_export_resource.go`.

One deliberate deviation: those resources put `RequiresReplace` on `scope_mrn`
only, leaving `space_id` without it. Here **both** carry it, because no mutation
moves a credential between scopes, so a `space_id` change is as much a new
credential as a `scope_mrn` change is. Omitting it would plan an in-place update
that cannot succeed.

`space_id` falls back to the provider-level `space` through
`ExtendedGqlClient.ComputeSpace`, as every space-scoped resource does.

Integration binding matches ownership **exactly**: a space-level integration
cannot use its organization's credential, or the reverse. The provider does not
validate this client-side — scope is not always known at plan time and the
server is the authority.

## Schema

```hcl
resource "mondoo_credential" "scanner" {
  space_id = "hungry-poet-123456"
  name     = "github-scanner"

  github_pat = {
    token    = var.gh_token
    base_url = "https://github.acme.com"
  }
}
```

| Attribute | Mode | Notes |
| --- | --- | --- |
| `space_id` | Optional, Computed, RequiresReplace | conflicts with `scope_mrn`; falls back to provider `space` |
| `scope_mrn` | Optional, Computed, RequiresReplace | conflicts with `space_id`; for organization-owned credentials |
| `name` | Required | **no** RequiresReplace — renames in place |
| *44 kind attributes* | Optional, `ExactlyOneOf` | generated; secret fields `Sensitive` |
| `mrn` | Computed | |
| `owner_mrn` | Computed | |
| `kind` | Computed | derived from which attribute is set; never an input |
| `health_status` | Computed | `UNKNOWN`/`HEALTHY`/`INVALID`/`ERROR`/`EXPIRED` |
| `health_checked_at` | Computed | null when never checked |
| `health_error` | Computed | |
| `expires_at` | Computed | **not an input** — see below |
| `created_at`, `updated_at`, `created_by` | Computed | |
| `field_values` | Computed, `map(string)` | non-secret fields as stored |
| `usages` | Computed, `list(object)` | see "usages is per slot" |

### expires_at is read-only

`CreateCredentialV2Input` accepts an `expiresAt` override, but
`RotateCredentialV2Input` does not — there is no mutation that changes an expiry
in place. Exposing it as an input would therefore make it a replacing edit, and
a replacing edit on a credential in use fails at apply (see "Replacement").

It is modelled **Computed-only**. The provider never sends `expiresAt`, so the
value always reflects what the provider reports about the secret. The manual
rotation-policy override is not available through Terraform; it can be added if
the API grows a rotate arm for it.

### usages is per slot, not per integration

`CredentialV2.usages` is a GraphQL union, currently one member:

```go
type CredentialV2IntegrationUsage struct {
    Mrn     string                // integration MRN
    Name    string                // display name, may be empty
    Purpose string                // which credential slot: "default", or a named slot
    Type    ClientIntegrationType // for icon and label
}
```

**One entry per credential slot, not per integration** — an integration filling
two slots from the same credential appears twice, by design. Modelled as a
`list(object({mrn, name, purpose, type}))`.

The field is non-nullable on purpose: a failed read is a GraphQL error, never an
empty list, because empty is the answer that makes deleting look safe. The
provider must surface a usages read error rather than defaulting to empty.

## Lifecycle

The SDK ships input types and enums only; every GraphQL response struct in this
repository is hand-declared. The read side lives in a new
`internal/provider/credential_gql.go`, following the `ExtendedGqlClient` method
convention in `gql.go`.

| Terraform | GraphQL | Payload |
| --- | --- | --- |
| Create | `createCredentialV2` | `{ credential: CredentialV2 }` |
| Read | `credentialV2(mrn)` | `CredentialV2` |
| Update (name) | `renameCredentialV2` | `{ credential: CredentialV2 }` |
| Update (secret) | `rotateCredentialV2` | `{ credential: CredentialV2 }` |
| Delete | `deleteCredentialV2` | `{ deletedMrn: String! }` |
| Import | `credentialV2(mrn)` | `CredentialV2` |

Update issues both mutations when both changed. Read is a real read — unlike
`integration_slack_resource.go`, whose `Read` is a deliberate no-op that must
**not** be copied here, because a credential has genuinely readable state.

## The five traps

### Trap 1 — the secret is write-only

No read returns it; `CredentialV2.fieldValues` is read from the row's redacted
copy and structurally cannot carry a secret. Secret attributes are populated
from config, marked `Sensitive`, and persisted to state; `Read` carries them
forward from prior state and never queries them. There is no drift detection on
the secret. This is the `aws_secretsmanager_secret_version` shape and is
documented as such.

Framework v1.19 supports `WriteOnly: true`, which would keep secrets out of
state entirely. Rejected: it requires Terraform >= 1.11 of every consumer, which
raises the provider's floor — a breaking change, out of scope for additive work.
Worth revisiting when the floor moves for other reasons.

### Trap 2 — rotation replaces the whole payload

`rotateCredentialV2` does not merge. A rotation that omits `baseUrl` resets a
GitHub Enterprise credential to github.com, and the health probe follows
`baseUrl`, so the credential then reprobes the wrong server. The same class of
bug resets an AWS region to us-east-1.

Update rebuilds the arm from the **entire** kind attribute and sends all of it,
every time, with no per-field diffing. The unit of change is the attribute, not
the field. The generator emits every field of every arm, so no field can be
omitted by oversight.

Per-field sensitivity makes the failure visible before it happens — a plan
renders `~ region = "eu-central-1" -> "us-east-1"` in the clear while the secret
stays redacted. This was the deciding argument for this shape over a secret map.

### Trap 3 — derivedFields must not be sent back

`fieldValues` mixes user-supplied fields, which round-trip, with fields the
server parsed out of the secret — gcp `project_id`, `client_email`. The server's
own model says it: "do not send it back on a rotation, because the input type
has no field for it."

No allowlist is needed. The generator emits attributes from the **input** arms
only, so a derived name has no attribute to be written through. Derived values
surface read-only in `field_values`, which is Computed and never Optional.

Confirmed by prototype: building a `gcp_service_account` secret rejects
`project_id` with `valid: [credentials_json]`.

### Trap 4 — exactly-one-of 44, server-enforced

`ExactlyOneOf` across the 44 generated attribute paths, evaluated by Terraform
core at plan time. The list is generated from `CredentialV2SecretInput`, so it
is total by construction rather than by maintenance — the constraint from the
original request is satisfied without a hand-written kind list anywhere.

### Trap 5 — delete is refused while in use

`Service.Delete` calls `blockingUsages` before touching the vault and returns
`FailedPrecondition` naming the integrations. Orphaning is refused deliberately;
from the server:

> the alternative — deleting the references too — would quietly convert a V2
> integration into a v1 one with no secret at all, which is exactly the
> transition the integrations service refuses to perform on purpose.

For ordinary destroy this is free: an integration referencing
`mondoo_credential.x.mrn` is destroyed first by the dependency graph, so the
credential is unreferenced by the time it is deleted. Every example wires the
reference that way.

`Delete` translates the `FailedPrecondition` into a diagnostic naming each
referencing integration **and its slot**, which the `usages` shape makes
possible.

## Replacement

Terraform's default replacement order is destroy-then-create. Because delete is
refused while in use, a replacing change to a credential an integration
references fails at apply: the destroy runs before the dependent update that
would release the reference. `create_before_destroy` inverts this — create the
replacement, let the integration move to the new MRN, then delete the old — but
`lifecycle` is user configuration and a provider cannot set it.

The design therefore minimises replacing edits.

### Changing the kind is refused at plan time

Kind is immutable. `Service.Rotate` rejects a kind change with
`InvalidArgument`: "credential %q is of kind %s and cannot be rotated to kind
%s". Only rename and rotate exist.

`RequiresReplace` would be the idiomatic Terraform answer for an immutable
attribute, but here it produces a plan that destroys a live credential and then
fails partway through apply whenever an integration references it. So a
`ModifyPlan` hook compares the kind in state with the kind in config and
**hard-errors**, with the migration recipe in the message: declare the new
credential alongside the old one, re-point the integration, remove the old one.

That flow applies cleanly in a single run with no `lifecycle` block, because the
three operations are independent graph nodes and Terraform orders them
correctly — create new, update integration, delete old.

### Scope changes still require replacement

`space_id` and `scope_mrn` keep `RequiresReplace`, matching
`export_s3_bucket.go`. There is no mutation that moves a credential between
scopes, and a scope change invalidates any existing binding anyway, since
ownership is matched exactly. This is the one remaining replacing edit, and it
is where the `create_before_destroy` note appears in the docs.

### Editing fields inside a kind attribute

An in-place rotation. Not a replacement, and needs none of the above.

## Integration binding

| Resource | Inline secret | Change |
| --- | --- | --- |
| `mondoo_integration_slack` | `slack_token` | Required to Optional; add `credential_mrn`; `ExactlyOneOf(slack_token, credential_mrn)` |
| `mondoo_integration_github` | `credentials` | Required to Optional; add `credential_mrn`; `ExactlyOneOf(credentials, credential_mrn)` |
| `mondoo_integration_aws` | `credentials` | Required to Optional; add `credential_mrn`; existing three-way `ExactlyOneOf(role, key, wif)` becomes four-way |

On AWS, `credentialMrn` is a fourth authentication mode. It substitutes for
`keyCredential` only — `roleCredential`'s vaulted secret is an AssumeRole
external ID rather than an AWS key, and `wifCredential` holds no server-side
secret — but it is mutually exclusive with all three.

GitHub's `credentialMrn` is also documented as conflicting with
`authMethod = APP`. The provider does not expose `auth_method`, so no validator
is needed; if `auth_method` is added later, that conflict must be added with it.

All three resources resend their secret on every update, including renames. That
is left exactly as it is — the server handles it, and changing it is neither
required by nor related to this work.

### The model transition forces replacement

All three field docs state that an integration cannot be moved between the
inline-secret and credential-backed models after creation. `credential_mrn`
therefore carries a `RequiresReplaceIf` that fires only on a null-to-known or
known-to-null transition, and does **not** fire when one credential MRN is
swapped for another, which the API supports in place.

```go
// requiresReplaceOnTransition: replace when the attribute appears or
// disappears, not when its value changes. The guards skip create and
// destroy, where every attribute transitions by definition.
func requiresReplaceOnTransition() planmodifier.String {
    return stringplanmodifier.RequiresReplaceIf(
        func(ctx context.Context, req planmodifier.StringRequest, resp *stringplanmodifier.RequiresReplaceIfFuncResponse) {
            if req.State.Raw.IsNull() || req.Plan.Raw.IsNull() {
                return
            }
            resp.RequiresReplace = req.StateValue.IsNull() != req.PlanValue.IsNull()
        }, ...)
}
```

Without it, removing `credential_mrn` from a config would plan an in-place
update, fail at apply, and re-propose the same update forever — because omitting
`credentialMrn` server-side keeps the current credential rather than clearing
it.

The modifier is on the new attribute only. Existing configurations have no
`credential_mrn` and never see it fire.

## Backward compatibility

Adding an optional attribute is not a breaking change.

The one change to existing schemas is Required to Optional on `slack_token`,
GitHub `credentials` and AWS `credentials`. This is mandatory: `ConflictsWith`
and `ExactlyOneOf` cannot reference a Required attribute, which is by definition
always set.

Required to Optional is a relaxation. Every existing configuration still sets
these attributes and is unaffected; the `ExactlyOneOf` validators mean a config
setting neither is rejected at plan time with a clear message rather than
silently accepted. No state migration.

## Testing

Acceptance tests follow the existing `testAcc*` convention: `resource.Test` with
`PreCheck: testAccPreCheck`, `testAccProtoV6ProviderFactories`, and configs built
by `fmt.Sprintf` helpers against `accSpace.ID()`, as in
`integration_slack_resource_test.go`.

`credential_resource_test.go`:

- create, read, rename in place, rotate, destroy
- organization scope via `scope_mrn`
- import by MRN
- delete refused while an integration references the credential
- changing the kind attribute rejected at plan time with the migration message

`credential_secret_test.go` — unit tests, no network:

- all 44 arms present in the generated schema
- `github_pat` and `aws` build the expected GraphQL input
- rotation sends every field of the attribute (trap 2)
- no attribute exists for a derived field name (trap 3)
- every field not on the visible list is marked `Sensitive`, and the visible
  list contains no field name the old `isSensitiveField` heuristic would have
  flagged — the regression guard for `macaroon` and `sas_url`
- `requiresReplaceOnTransition` fires on null-to-known and known-to-null, and
  not on known-to-known, create or destroy

Integration binding tests extend the three existing test files with a
`credential_mrn` case referencing `mondoo_credential.test.mrn`.

**These tests cannot be run in this environment.** `TestMain` requires a live
organization service account and gates the whole package, so even the unit tests
above will not execute without `MONDOO_CONFIG_BASE64`. They will be delivered
written and compiling; `go build ./...` and `go vet ./...` are the verification
available here. This limitation is pre-existing.

## Out of scope

- A `mondoo_credential` **data source**. Not requested; worth adding later for
  referencing credentials created outside Terraform.
- `testCredentialV2`. It maps to an imperative action, not resource state; the
  health fields already surface the probe that create and rotate perform.
- `credentialV2Kinds` descriptor consumption. The generator reads the SDK input
  types, so the descriptor's human copy is not needed. It exists if the docs
  ever want titles and descriptions.
- The `expiresAt` create override.
- Exposing `auth_method` on the GitHub integration.
- Credential binding on integrations beyond the three named.
- Changing the resend-secret-on-every-update behaviour of the three
  integrations.

## Risks

**Generator output size.** 44 attributes across roughly 130 fields produces a
large generated file. It is generated and gofmt'd, so this is a review-diff
concern rather than a maintenance one, but the first PR will be big.

**The visible-field list is hand-maintained.** Small, and it fails safe — a
field left off is redacted rather than exposed — but it does need extending when
a kind adds a non-secret field, or that field's diff shows as
`(sensitive value)`. This is the one piece of per-kind knowledge that does not
come from the SDK, and it is deliberately the piece whose failure mode is
cosmetic.

**Terraform-native ergonomics.** This shape cannot `for_each` across mixed kinds
the way a secret map could; a config managing many credentials of different
kinds needs one resource block per kind. Accepted in exchange for plan-time
validation and visible non-secret diffs.
